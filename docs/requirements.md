# 要件定義

## 1. 背景

ボランティア活動の現場で、**役割ごと・時間帯ごとに人を配置する**必要がある。現在はスプレッドシートや紙で管理しており、以下の課題がある。

- 誰がいつどこにいるかの一覧性が低い
- 人手が足りない時間帯の発見が遅れる
- 単発参加のボランティアが多く、その都度の調整コストが高い

## 2. 用語

| 用語 | 定義 |
|---|---|
| **場所（place）** | 人を配置する対象。複数あり、1つの場所に複数人を配置できる |
| **枠（slot）** | 「いつ・どこに・何人必要か」の定義。日付 × 場所 × 時間帯 × 必要人数 |
| **可用性（availability）** | ある人が「その日、何時から何時まで入れるか」の申告。1人が1日に複数持てる |
| **割り当て（assignment）** | 枠に対して実際の人を紐づけたもの |
| **ボランティア** | 単発参加が多い。可用性を自分で登録する |
| **職員** | 継続的に関わる。ボランティアで埋まらない枠を埋める |
| **充足** | 枠の必要人数に対して割り当て人数が足りている状態 |

## 3. 利用者と役割

| 役割 | できること | 認証 |
|---|---|---|
| **ボランティア** | 可用性の登録（応募）、配置表の閲覧 | なし（URL/QRを知っていれば可） |
| **管理者** | 枠の作成、割り当て、人の管理 | なし（URLを知っていれば可。操作時に記名する） |

**認証は行わない。** 管理者を識別する仕組みは持たず、URL（QRコード）を知っている人は誰でも管理操作ができる。誰が変更したかは操作時の記名で `_log` に残す。

この判断の帰結として、**連絡先は画面に一切表示しない**。管理者だけに見せる手段が無いため、連絡先が必要なときは管理者がスプレッドシートを直接参照する。

利用者はGoogleアカウントを持たない前提。PCに不慣れな人が多い。

## 4. 機能要件

### 4.1 枠の管理（管理者）

- 場所を複数登録できる
- 枠を日付・場所・開始/終了時刻・必要人数で作成できる
- 時刻は**10分単位**で指定できる
- **週テンプレートから枠を一括生成できる**（曜日ごとのパターンを定義）
- **前日・前週の枠をコピーできる**
- 枠ごとに「職員が最低1名必要」の指定ができる

> 日常運用では、毎回ゼロから枠を作ることはない。テンプレートとコピーが使われなければツールは定着しない。最優先機能と位置づける。

### 4.2 可用性の登録（ボランティア／管理者代理）

- 名前・連絡先・日付・入れる時間帯を入力して送信できる
- 1日について複数の時間帯を登録できる（例: 9:00-12:00 と 14:00-16:00）
- 「終日OK」のショートカットがある
- アカウント作成・ログインは不要
- 管理者は代理で入力できる（電話やLINEでの申し込みに対応するため）
- 職員は毎回入力せず、**既定で勤務時間帯すべてを可用とみなす**

### 4.3 割り当て（管理者）

- 枠を選ぶと、その枠に入れる**候補者リスト**が表示される
- 候補者の条件:
  - その時間帯の可用性がある
  - **同じ時間帯に別の場所へ割り当てられていない**（ダブルブッキング防止）
- 候補者の並び順:
  1. **ボランティアが上、職員が下**（職員は視覚的に区別する）
  2. 同種別内では、その日の割り当て時間が少ない人が上（負担の平準化）
- 候補者をクリックすると割り当てられる／解除できる
- 可用性が枠を部分的にしか満たさない人は、別セクションに控えめに表示する（管理者判断で割り当て可能）

### 4.4 充足状況の可視化（管理者）

- 枠ごとに「必要人数 / ボランティア数 / 職員数」を表示する
- **ボランティアだけでの充足**と**職員込みの充足**を分けて表示する
  - 前者を見ながらボランティアを割り当て、後者で完了判定するため
- 職員必須の枠に職員が未配置の場合は警告する
- **未充足枠の一覧**（職員配置待ちリスト）を別画面で表示できる

### 4.5 配置表の閲覧（全員）

- 縦軸=場所、横軸=時間のタイムライン形式で1日分を表示する
- 日付を切り替えられる
- 充足状況が色で判別できる
- 印刷／PDF出力できる（会場のネットワークが不安定なため紙の配布が必要）
- 公開ビューでは連絡先を表示しない（表示名の粒度は設定で切り替え）

### 4.6 整合性の警告

- 割り当て済みの人が可用性を取り下げた／変更した場合、**割り当ては自動削除せず警告表示にとどめる**
  - 自動削除は事故のもとになる。管理者が気づいて判断する
- 同一人物が同時間帯に複数の場所へ割り当てられている場合は警告する

## 5. 非機能要件

- スマートフォンでの閲覧・入力に対応する
- 画面の初期表示は数秒以内
- 操作は「タップ→選ぶ」の2ステップを基本とし、**ドラッグ&ドロップは使わない**（操作に不慣れな人にとって誤操作と不安の原因になる）
- 保存結果を必ず明示する（「保存しました」の表示）
- 想定規模: 場所10件程度、1日あたり枠100件程度、年間の割り当て数万行

## 6. スコープ外

以下は**作らない**。実装を提案することもしない。

- メール・LINE・その他の通知／連絡機能
- 自動割り当て（組み合わせ最適化）
- 勤怠管理・給与計算・労働時間集計
- 複数管理者の同時編集における競合解決（応募受付のロックを除く）
- ボランティア個人のマイページ・ログイン機能
- 他人のカレンダーを読んで空きを判定する機能（アカウント不要の前提と両立しない）

## 7. 将来の任意拡張

現時点では実装しないが、設計上の余地は残しておく。

- **ICSフィード配信**: 個人別トークン付きURLでカレンダー購読を提供する。`ContentService.MimeType.ICAL` で実現可能。ただし外部ICSの購読は反映が遅く（Googleカレンダーで半日以上かかることがある）、期待値の調整が必要なため後回しとする
- 当日の出欠チェック機能
- 参加履歴の集計（名寄せ前提）
